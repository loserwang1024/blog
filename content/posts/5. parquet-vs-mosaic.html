Parquet vs Mosaic 文件格式详解

用"图书馆"的比喻，帮你从零理解列式存储的核心概念

引言：Paimon 社区引入 Mosaic 文件格式

最近，Apache Paimon 社区由 Jingsong Li 发起了一项[DISCUSS] Introduce a new file format for wide table的提案，提出了一种名为 Mosaic 的全新文件格式（POC 实现），专门针对超宽表（10,000+ 列）场景做了极致优化。

在万列宽表的 benchmark 中，Mosaic 展现了惊人的优势：文件大小仅为 Parquet 的 1/15，投影读取单列延迟快 21 倍。这些收益的本质来源是什么？为什么传统的 Parquet 格式在列数膨胀时会遇到瓶颈？Mosaic 做了哪些关键的架构设计来解决这些问题？同时，它又牺牲了什么？

本文将从最基本的概念讲起，用通俗的比喻解释 Parquet 的文件结构（Row Group、Column Chunk、Page、Footer），再对比 Mosaic 的桶式混合设计，帮助理解这两种格式在不同场景下的表现差异。

先打个比方：一张"学生成绩表"

假设你有一张表，记录了全校 1000 名学生的信息：

姓名语文数学英语物理...
张三85927888...
李四90769582...
..................

行式存储（如 MySQL）：像一本花名册，每翻一页就是一个学生的所有信息。要查"所有学生的数学成绩"，你得翻遍每一页，从中挑出数学那一栏。

列式存储（如 Parquet）：像一个档案柜，每个抽屉只放一科的成绩单——第一个抽屉全是语文分数，第二个全是数学分数……要查数学成绩？直接拉开"数学"那个抽屉就行，不用碰其他科目。

但如果你有 10,000 个科目（宽表），这个档案柜就有一万个抽屉。光是柜门上的目录标签（元数据）就占了半面墙——这就是 Parquet 遇到的问题。

Parquet 文件整体结构

一个 Parquet 文件从上到下由以下几部分组成。你可以把它想象成一本书：

Magic Number: "PAR1" (4 字节)
文件开头的"身份证"，告诉程序"我是 Parquet 格式"
▼
Row Group 0（行组 0）
前 N 行的数据，内部按列拆分
▼
Row Group 1（行组 1）
接下来 N 行的数据
▼
... 更多 Row Group ...
文件可能有很多行组
▼
Footer（页脚元数据）
整个文件的"目录"——记录了每一列在文件中的位置、类型、统计信息等
▼
Footer Length (4 字节) + Magic "PAR1"
文件末尾，告诉程序 Footer 有多长

📦 什么是 Row Group（行组）？

把 1000 行数据想象成一本书。Row Group 就是把这本书分成几章，比如每 500 行一章。这样做的好处是：读数据时不用加载整本书，只读需要的那一章就行。

每个 Row Group 内部，数据按列拆分成多个 Column Chunk：

Row Group 0 的内部结构（假设表有 3 列）
Column Chunk: "姓名"
Page 0: 张三, 李四, 王五...
Page 1: 赵六, 钱七...
Column Chunk: "数学"
Page 0: 92, 76, 88...
Page 1: 95, 80...
Column Chunk: "英语"
Page 0: 78, 95, 82...
Page 1: 91, 73...

📄 什么是 Column Chunk（列块）？

在一个 Row Group 里，每一列的数据被单独打包，这就是 Column Chunk。它就是档案柜里的"一个抽屉"。

比如 Row Group 0 有 500 行、3 列，那就会有 3 个 Column Chunk，分别存"姓名"、"数学"、"英语"的数据。

好处：如果你只查"数学"成绩，只需要读"数学"那个 Column Chunk，其他列根本不碰。

📃 什么是 Page（页）？

Column Chunk 内部还可以再分成更小的单元，叫做 Page。这是 Parquet 中最小的读取和压缩单位。

你可以把 Column Chunk 想象成一个抽屉，Page 就是抽屉里的一叠文件。每叠文件独立压缩，这样即使只需要前几行，也不用解压整个抽屉。

Page 有几种类型：

Data Page
存实际数据值，包含 repetition levels 和 definition levels（用于嵌套类型和 NULL 处理）
Dictionary Page
字典编码时使用，存储不重复的值列表（如只有"男""女"两个值，就存一个字典）
Page Header
每个 Page 开头的元信息：编码方式、压缩后大小、未压缩大小、数据条数等

📋 什么是 Footer（页脚）？

Footer 是整个 Parquet 文件的"总目录"，放在文件末尾。它用 Thrift 格式序列化，记录了：

Schema（模式）
表有哪些列，每列叫什么名字、是什么类型。对于嵌套类型，还有完整的树状结构。
Row Group 元数据
每个 Row Group 有多少行，以及其中每个 Column Chunk 在文件中的偏移位置、压缩/未压缩大小。
列统计信息
每列的 min、max、null_count 等。查询引擎可以据此跳过不相关的 Row Group（谓词下推）。
宽表下的致命问题

Footer 为每一列都存了完整的元数据。10 列时可能只有几 KB，但 10,000 列时，Footer 可能膨胀到数 MB——而且每次读文件都得全量解析这个 Footer，哪怕你只需要 1 列。

完整读取流程

当查询引擎要读 Parquet 文件中的某一列时，流程是这样的：

① 读文件末尾 8 字节 → 得到 Footer 长度
② 读取整个 Footer → 反序列化（解析全部列的元数据）
③ 从 Footer 中找到目标列的 Column Chunk 偏移量
④ Seek 到对应位置 → 逐 Page 解压、解码
⑤ 返回数据

步骤②是瓶颈——列越多，Footer 越大，解析越慢。

Mosaic 文件整体结构

Mosaic 的关键创新：在列和文件之间加了一层"桶"（Bucket）。回到档案柜的比喻——它不是一万个小抽屉，而是把一万门课按名称分成 100 个大柜子，每个柜子里放约 100 门课的成绩单，每个柜子整体上锁（压缩）。

Row Group 0: Bucket Data
多个 Bucket 压缩块，只存非空桶
▼
Row Group 1: Bucket Data
...
▼
Schema Block（模式块）
列名用 BPE + Front Coding 压缩，极致节省空间
▼
Row Group Index（行组索引）
varint 编码，记录每个桶的偏移和大小
▼
Footer（固定 32 字节！）
无论多少列，永远只有 32 字节

🪣 核心概念：Bucket（桶）

10,000 列按名称排序后，均匀分成约 100 个桶：

bucketId = 列的排序位置 × 总桶数 / 总列数

Bucket 0
acc_x, acc_y, acc_z,
altitude, angle_...
Bucket 1
battery_level,
battery_temp,
brake_...
Bucket 2
engine_coolant_p,
engine_coolant_t,
engine_oil_...
...
更多桶
Bucket 99
wind_dir,
wind_speed,
yaw_rate
为什么按名称排序分桶？

因为现实中的列名往往有共同前缀（如 engine_coolant_temp、engine_coolant_pressure）。排序后它们自然聚在一起，同桶内的数据更相似 → 压缩率更高，而且查询相关列时只需读少数几个桶。

🔍 Bucket 内部长什么样？

每个 Bucket 是一个独立压缩块，内部是列式存储。和 Parquet 不同的是，它用极简的方式标记每列的编码，没有 Page Header 等额外结构：

Bucket 2 内部结构（解压后）
Encoding Flags: 每列 2 bit — [PLAIN, CONST, ALL_NULL, DICT, ...]
Has-Nulls Flags: 每列 1 bit
CONST 元数据: coolant_pressure = 101.3 (只存1个值!)
DICT 元数据: oil_grade → {5W-30, 10W-40} (2个值)
Null Bitmaps: 标记哪些行是 NULL
Column Data: PLAIN 列的原始数据 + DICT 列的 bit-packed 索引

四种编码的含义：

编码使用场景存储开销
ALL_NULL该列在这个 Row Group 里全是 NULL0 字节（仅 encoding flag 中 2 bit）
CONST所有非空值都一样（如某传感器一直读 0）只存 1 个值
DICT2-255 个不同值字典 + bit-packed 索引（极省空间）
PLAIN值很多样原始值逐行存储
宽表杀手锏

宽表中大量列在某段时间内可能全为 NULL 或只有一个常量值。ALL_NULL 列的开销仅 2 bit，CONST 列只多存一个值——10,000 列中 8,000 列为空，成本几乎为零。而 Parquet 对每列都有固定的 Page 头等结构开销。

🗜️ 列名怎么压缩？

10,000 个列名 × 平均 80 字节 = 800KB 纯列名。Mosaic 用两招压缩：

Front Coding（前缀编码）
列名排序后，每个只存"和前一个共享了多少字节 + 新增的部分"。
例如：
• engine_coolant_pressure → 完整存储
• engine_coolant_temperature → 共享 16 字节 + "temperature"
（Lucene、LevelDB 都用这个技术）
BPE（字节对编码）
统计列名中高频出现的子串（如 _status、_value），用一个单字节 token 替代。
最多 128 条规则，可以把 _timestamp 这种 10 字节子串压成 1 字节。
仅限 ASCII 列名。

完整读取流程

当查询引擎要从 Mosaic 文件中读取某一列时，流程如下（假设要从 10,000 列中读取 engine_coolant_temp 这一列）：

1
读取文件末尾 32 字节 → 得到 Footer

固定大小，一次 I/O 搞定。从中拿到两个关键地址：schemaBlockOffset 和 indexOffset，以及 numBuckets=100。

32 字节 → 得到 schemaBlockOffset=0x5F200, indexOffset=0x5FA00, numBuckets=100
2
读取 Schema Block → 找到目标列属于哪个桶

Seek 到 schemaBlockOffset，读取并解压 Schema Block。在列名有序列表中找到 engine_coolant_temp，根据它在排序中的位置计算：

sortedPosition=2347, bucketId = 2347 × 100 / 10000 = 23

同时得到该列在桶内的本地位置（第几列）和数据类型信息。

3
读取 Row Group Index → 找到 Bucket 23 在文件中的物理位置

Seek 到 indexOffset，读取 varint 编码的 Row Group Index。从中找到 Row Group 0 里 Bucket 23 的条目：

bucketId=23, offset=0x1A400, compressedSize=4096, uncompressedSize=7800
4
Seek 到 Bucket 23 → 读取并解压这一个桶（4KB）

只读 4KB 压缩数据，用 Zstd 解压得到 7.8KB。这个桶里约有 100 列的数据——但 其余 9,900 列的数据完全没碰。

只解压了 1/100 的数据！其余 99 个桶完全跳过。
5
在桶内定位目标列 → 解码数据

桶解压后，根据 encoding flags 找到 engine_coolant_temp 的编码方式（比如 PLAIN），跳过桶内其他列的数据区，直接读取目标列的值：

读 encoding flag → PLAIN
读 null bitmap → 标记哪些行为 NULL
读 data → [92.3, 91.8, NULL, 93.1, ...]
6
返回数据

如果有多个 Row Group，对每个 Row Group 重复步骤 3-5（Schema 只需解析一次）。

I/O 对比：读 1 列时实际发生了什么？

Parquet：读 Footer（可能几 MB）→ 全量反序列化 10,000 列的元数据 → Seek 到目标 Column Chunk → 逐 Page 解压
Mosaic：读 Footer（32 字节）→ 读 Schema Block（找桶号）→ 读 Index（找桶位置）→ 只解压 1 个桶（~4KB）

Parquet 的瓶颈在步骤 2（解析 MB 级 Footer），Mosaic 最重的步骤是解压一个桶——而那个桶可能只有几 KB。这就是为什么读 1/10,000 列时 Mosaic 比 Parquet 快 21 倍。

根本原因：三个维度的对比

① 元数据规模：O(n) vs O(1)

Parquet: Footer 大小随列数线性增长。10,000 列 → MB 级 Footer，每次读文件都要全量解析。
Mosaic: Footer 固定 32 字节。Schema 信息独立存放且经过 BPE + Front Coding 压缩。

② I/O 粒度：逐列 vs 按桶

Parquet: 每列一个 Column Chunk，projection 时逐列 seek + 读取。10,000 列中读 10 列 = 10 次 I/O。
Mosaic: 10,000 列分成 ~100 个桶，读 10 列可能只涉及 1-3 个桶。每个桶是一个独立压缩块，一次解压搞定。

③ 稀疏列开销：有固定开销 vs 几乎为零

Parquet: 即使一列全是 NULL，仍有 Column Chunk 头、Page Header、Definition Levels 等结构。
Mosaic: ALL_NULL 列只占 encoding flag 中的 2 bit，CONST 列只多存 1 个值。宽表中大量稀疏列的开销趋近于零。

一句话总结

Parquet 是通用的好格式，但它的 per-column 元数据设计在列数膨胀到万级时成为瓶颈。Mosaic 通过"桶分组 + 固定 Footer + 列名压缩 + 自适应编码"，把随列数线性增长的开销降到了常数级，从而在超宽表场景下获得数量级的优势——代价是放弃了复杂类型和统计下推。

Mosaic 不如 Parquet 的场景

凡事有代价。Mosaic 为超宽表做了极端优化，但在以下场景中反而不如 Parquet（不考虑谓词下推）：

1
列数少（几十到几千列）

Parquet 的 Footer 本身很小（几十 KB），一次读完就拿到全部信息（schema + 每列位置 + 统计），一步到位。Mosaic 硬生生多了 Schema Block 和 Index 两次额外寻址，省下的空间微乎其微，反而因为多跳和桶结构增加了不必要的复杂性。

2
投影比例高（读大部分列）

Mosaic 最大的优势是"跳过大量桶"。如果你要读 8,000/10,000 列，可能全部 100 个桶都得解压，桶抽象完全失效，和全量扫描无异。而 Parquet 按列精确读取，读多少列就读多少 Column Chunk，每个 Chunk 就是一列的数据——不多不少。

3
数据稠密，稀疏列少

ALL_NULL/CONST 编码是 Mosaic 压缩文件大小的杀手锏（宽表中大量列为空或常量）。如果每列都有丰富多样的数据，这个压缩红利消失，文件大小优势大幅缩水——甚至可能因为桶结构的额外开销（encoding flags、null bitmaps 等）反而更大。

4
列的数据分布差异大

Parquet 每列独立压缩，能针对每列的数据特征选最优策略（低基数走字典、时间戳走 delta encoding、浮点数走 byte stream split 等）。Mosaic 将同桶内不同类型、不同分布的列混在一起用 Zstd 一把压缩，对异构数据的压缩率天然不如逐列精细优化。

5
需要复杂类型（ARRAY、MAP、嵌套结构）

Mosaic 只支持 18 种扁平类型（BOOLEAN 到 TIMESTAMP_LTZ）。遇到嵌套数据（JSON 展开、Protobuf 消息等需要 ARRAY/MAP/ROW 的场景）直接不可用。Parquet 通过 Dremel 编码（repetition levels + definition levels）原生支持任意深度的嵌套结构。

6
Schema 频繁变更（尤其是列重命名）

桶分配依赖列名在字典序中的位置（bucketId = sortedPosition × numBuckets / numColumns）。列被重命名后排序位置改变，可能从一个桶迁移到另一个桶，导致历史文件和新文件的桶布局不一致，增加上层 Schema Evolution 的协调复杂度。

Mosaic 的"甜蜜区"

Mosaic 的设计哲学押注的是"超多列 + 高稀疏 + 少量投影"这个组合（典型场景：IoT 设备宽表、ML 特征存储、多模态元数据表）。偏离这个组合越远，收益越小。在列数不多、数据稠密、或需要全量扫描的场景下，Parquet 的 per-column 精确设计仍然是更优解。
